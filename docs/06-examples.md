# 06 — Example workflows (all synthetic)

Three examples, each with mock MCP servers, seeded data generators, a task prompt, an MCP
config for Claude Code, and a Makefile. They double as integration tests and as the demo.
All names are fictional (company "Northwind Lanterns Co.", products like "Brass Hurricane
Lantern", people like "Dana Oyelaran"). No real data anywhere.

Each example directory is its own Amber project root: it has an `amber.toml` (servers
pointing at the mock servers with `AMBER_SCENARIO`), its own `.amber/` and `programs/`
(the examples commit their `programs/` so readers can inspect the output without running
anything). Run `amber` commands from inside the example directory or pass `--project PATH`.

Shared: `examples/_shared/synth.py` (seeded RNG → ids, names, dates, amounts),
`examples/_shared/server_slack.py` (`list_channels()`, `post_message(channel, text)` → writes
to `examples/<ex>/.outbox/slack.jsonl` and returns `{"ok": true, "ts": "..."}`; `post_message`
annotated `readOnlyHint=False`), `examples/_shared/mcp_common.py` (MCPServer helpers, scenario
env var `AMBER_SCENARIO`).

Mock servers use the high-level v2 API:

```python
from mcp.server import MCPServer
mcp = MCPServer("shop")
@mcp.tool()                     # schema from type hints + docstring; add annotations for effects
def list_orders(since: str, until: str) -> list[dict]: ...
if __name__ == "__main__": mcp.run()   # stdio (check installed docs for the transport kwarg)
```

Add `annotations=ToolAnnotations(readOnlyHint=True)` on read tools where the API supports it
(verify in installed version); otherwise Amber falls back to name heuristics.

## 1. `weekly-report` (the headline demo)

**Story:** every Monday, pull last week's orders, compute RFM shifts and top products, write a
short narrative, post to Slack. 3 recordings with `--input week=2026-W42|W43|W44`.

**Server `shop`** (SQLite file generated by `scenario.py`, 12 weeks, ~900 orders, 120
customers, 14 products):
- `week_range(week: str) -> {"start": "YYYY-MM-DD", "end": "YYYY-MM-DD"}`
- `list_orders(since: str, until: str) -> list[{"id","customer_id","created_at","total","items":[{"sku","qty","price"}]}]`
- `list_customers() -> list[{"id","name","segment","first_order_at"}]`
- `top_products(since, until, n: int = 5) -> list[{"sku","name","revenue","units"}]`
- `rfm_snapshot(as_of: str) -> list[{"customer_id","r","f","m"}]` (available so the agent can
  compare weeks; the transform hole will likely compute shifts from two snapshots)

Scenario B (`make drift`): `list_orders` returns `amount` instead of `total` → `ResultShapeGuard`
hard → doctor `degraded/fallback`.

**Task prompt** (`task.md`): "Pull the orders for week {week}, compute how RFM segments shifted
versus the previous week and the top 5 products, then post a 5-sentence summary to #eng on
Slack. Use the shop and slack tools only."

**Expected compiled shape:** 4–6 deterministic calls, 1 transform (segment shift), 1 judgment
(summary text), 1 write (post_message). `amber run` → 0 agent turns, 1 llm call.

## 2. `issue-triage`

**Story:** triage new GitHub issues: label by area, detect duplicates, post a digest.

**Server `github`** (in-memory from `scenario.py`, 40 issues, 6 areas, 4 duplicate pairs):
- `list_issues(state: str = "open", since: str | None = None) -> list[{"number","title","body","labels","created_at"}]`
- `get_issue(number: int) -> {...}`
- `search_issues(query: str) -> list[{"number","title"}]`
- `add_labels(number: int, labels: list[str]) -> {"ok": true}` (write)
- `add_comment(number: int, body: str) -> {"ok": true, "id": int}` (write)

Scenario B: label taxonomy changes (`area:*` → `kind/*`), `add_labels` rejects unknown labels
→ `ErrorGuard` → fallback shows the agent re-deriving labels.

**Expected compiled shape:** judgment steps per issue batch (labels + duplicate_of with
`confidence`), deterministic writes, one digest judgment, one Slack post. Demonstrates
judgment-heavy workflows still saving tokens (the agent's exploration is gone; the llm()
calls are small and schema-bound).

Inputs: `--input since=2026-10-27` etc. Record 3 runs on three "days" (`scenario.py --day N`
shifts which issues are new).

## 3. `price-watch`

**Story:** check a catalog site for price/stock changes and alert.

- `site/` static HTML: `index.html` (6 products with `.price` and `.stock` spans) served by
  `python -m http.server 8765 --directory site` (Makefile target `serve`).
- MCP: `@playwright/mcp` via `npx -y @playwright/mcp@latest` (Node ≥ 18 required; document).
  Recorded tools: `browser_navigate`, `browser_snapshot` / `browser_evaluate` or whatever the
  current server exposes — Amber records them as `playwright.<tool>`.
- Server `alerts` (shared Slack mock reused as `alerts.post_message`).

Scenario B: prices change *and* the CSS class is renamed `.price` → `.cost` → the deterministic
extraction step's result shape changes → guard → doctor → fallback → recompile (v2 uses the
new selector). This is the "self-healing" GIF.

Inputs: `--input product=all` / `--input product=lantern-brass`.

**Expected compiled shape:** navigate + snapshot deterministic, extraction as a transform hole
(parsing the snapshot text into `{sku: {price, stock}}`), judgment "is this change notable?"
with schema `{notable: bool, reason: str}`, conditional alert post.

## Makefile contract (each example)

```
make record     # 3 recordings with the example's inputs (needs claude CLI logged in)
make align      # amber align <wf> --show
make compile    # amber compile <wf>
make verify     # amber verify <wf>
make run        # amber run <wf> --input <default> --allow-writes
make drift      # switch scenario to B (regenerates data / site)
make heal       # amber run --fallback agent --allow-writes ; amber compile --refresh ; amber verify
make demo       # record align compile verify run
make clean      # remove .amber/, .outbox/, programs/
```

`examples/README.md` documents expected console output for each step (copy from a real run,
synthetic values) so readers know what "good" looks like.

## Recording tips to put in the user guide

- Keep the task prompt tight and tool-oriented; say which tools to use.
- Record 2–3 runs with **different inputs**; identical inputs give the compiler nothing to
  generalize from.
- Prefer MCP tools over Bash/Read for anything the program must repeat; builtins are
  supported only for a safe subset.
- Declare inputs with `--input` so provenance is exact.
