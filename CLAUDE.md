# CLAUDE.md — Amber

Amber is an open-source **compiler for agent runs**. You record an AI agent doing a
workflow a few times (Claude Code, the Claude Agent SDK, or any MCP-speaking harness),
and Amber compiles those runs into a **neuro-symbolic program**: deterministic Python for
the parts that are mechanical, small schema-validated `llm()` calls for the parts that need
judgment, plus **replay tests** generated from the recordings. The program then runs on a
schedule at a fraction of the tokens, with guards, a `doctor` that detects drift, and a
fallback that hands control back to the agent and recompiles.

This file is the contract for working in this repository. `PLAN.md` is the phased build
plan; `docs/` holds the specifications each phase implements. Read `PLAN.md` fully before
writing code. Specs win over your assumptions; if a spec is wrong or impossible, say so in
`PROGRESS.md` and propose the smallest fix, do not silently diverge.

## Non-negotiables

1. **Synthetic data only.** Every example, fixture, screenshot, GIF and benchmark uses data
   generated by code in this repo (seeded generators). Never paste real customer, employer
   or third-party data, real Slack/GitHub exports, or real credentials. Example company and
   product names must be obviously fictional.
2. **Deterministic compiler, typed holes.** The program skeleton is generated by code from
   the aligned traces (`src/amber/compile/codegen.py`). The LLM only fills typed holes
   (transform functions, judgment prompts/schemas) and every hole fill is verified against
   the recordings before it is accepted. Never let the model write the whole program
   free-form.
3. **Replay before live.** `amber compile` must produce a program that passes
   `amber verify` against every source trace before it is marked usable. A program that
   fails replay is not a program.
4. **Guards on every live call.** Live runs enforce tool allowlists, result-shape checks,
   call and token budgets, and the write-effect policy (`docs/05-runtime.md`). No guard
   bypass flags other than the documented `--allow-writes` and `--no-fallback`.
5. **Measured numbers only.** README and docs may cite research numbers with their source
   (FlashScript, arXiv 2610.33876) but any number presented as Amber's own comes from
   `bench/` output committed with model, date and command. No invented token savings.
6. **No secrets in the repo.** API keys only via environment variables. `.amber/` runtime
   state and `*.env` are gitignored. Add a pre-commit secret scan (gitleaks or
   detect-secrets).
7. **Tests are part of the task.** A phase is done when its acceptance checks in `PLAN.md`
   pass locally with the exact commands listed there. Do not mark a checkbox before the
   command has been run and its output recorded in `PROGRESS.md`.
8. **Harness-agnostic by design.** Nothing in `trace/`, `align/`, `compile/` or `runtime/`
   may import Claude-specific code. Harness specifics live only in `adapters/` and
   `models/`.

## Stack (pinned)

| Concern | Choice | Notes |
|---|---|---|

| Agent SDK | `claude-agent-sdk` ≥ 0.2 (optional extra `[sdk]`) | same message shapes as stream-json |
| Web panel | `fastapi` + `jinja2` + HTMX (vendored), `uvicorn` | read-mostly; no JS build step |
| Schema inference | `genson` | infer result-shape schemas from recordings |
| Tests | `pytest` ≥ 9, `pytest-asyncio`, `hypothesis` for canonicalization | unit tests never touch the network |

## Commands you will use

```bash
uv sync --all-extras                  # install everything
uv run amber --help                   # CLI
uv run pytest -q                      # unit tests (fast, offline)
uv run pytest -q -m live              # live tests (need ANTHROPIC_API_KEY or a logged-in claude CLI)
uv run ruff check . && uv run ruff format --check .
uv run pyright
uv run python bench/run_bench.py --example weekly-report --runs 3
make demo                             # end-to-end on examples/weekly-report (record → compile → verify → run)
```

## Coding conventions

- Python 3.12+. Type hints everywhere; `pyright` must pass. Prefer `dataclass(frozen=True)`
  for internal value objects and Pydantic models for anything serialized.
- Async for MCP and model calls; the CLI wraps with `anyio.run`/`asyncio.run` at the edge.
- All JSON written to disk is canonical: UTF-8, `sort_keys=True`, `ensure_ascii=False`,
  newline at EOF. Use `amber.util.json.dumps_canonical`.
- Every user-facing error is an `AmberError` subclass with a one-line message and a hint.
  Exit codes: `0` ok · `1` error · `2` usage · `3` verify failed · `4` guard stopped the run ·
  `5` doctor found drift.
- Logging via `logging` with a `rich` handler; `AMBER_LOG=debug` enables debug.
- No `shell=True`. Subprocesses use argument lists. The `builtin.Bash` backend is the only
  place that executes recorded shell strings, and it does so under the policy in
  `docs/05-runtime.md`.
- Keep modules under ~400 lines; split by responsibility, not by convenience.
- Docstrings on public functions; comments explain *why*, not *what*.
- Commit style: Conventional Commits (`feat(align): ...`, `fix(runtime): ...`). One phase ≈
  several small commits. Never commit `.amber/`, `*.env`, generated program outputs under
  `examples/*/.amber/`.

## How to work this plan

1. Read `PLAN.md` and the docs it references for the current phase.
2. Append a dated entry to `PROGRESS.md` when you start a phase: what you will build, which
   decisions you are taking from `docs/11-decisions.md`.
3. Write the tests for the phase first where the spec gives exact behaviour (trace mapping,
   canonicalization, alignment, cassette replay). Then implement.
4. Run the phase's acceptance commands exactly as written. Paste the key output lines into
   `PROGRESS.md`. Only then tick the boxes in `PLAN.md`.
5. If a spec conflicts with reality (an API changed, a flag does not exist), verify against
   the installed version (`uv run python -c "from importlib.metadata import version; print(version('mcp'), version('anthropic'))"`,
   `claude --help`), fix the spec in `docs/` with a short note, and continue.
6. Ask the user only for items marked **ASK** in `docs/11-decisions.md`. Everything else has
   a default; take it and note it.
7. Phases 2, 8 and 9 contain independent work items that can run in parallel subagents
   (see "Parallel work" in `PLAN.md`). Alignment, codegen and cassette replay share models
   and must be done sequentially by one agent.
8. Keep `README.md` truthful at every commit: features listed there must exist and have a
   test.

## Definition of done for v0.1

- `uv tool install amber-compiler` (or `uvx --from amber-compiler amber`) gives a working
  `amber` CLI on macOS and Linux.
- `make demo` on a clean checkout with the `claude` CLI logged in (or `ANTHROPIC_API_KEY`
  set) records 3 runs of `examples/weekly-report`, compiles, verifies 3/3, and runs the
  compiled program live against the mock servers with 0 agent turns and ≤ 2 `llm()` calls.
- `examples/price-watch` demonstrates drift: `make drift` changes the site, `amber run`
  stops on a guard, `amber doctor` reports `degraded` with recommendation `fallback`,
  `amber run --fallback agent` records a new trace, `amber compile --refresh` produces v2
  that verifies against all traces.
- `bench/results.md` contains measured numbers for all three examples.
- CI green on Python 3.12 and 3.13; coverage ≥ 80% on `trace/`, `align/`, `compile/`,
  `runtime/backends/cassette.py`.
- README has: 60-second demo GIF, install, the 6-command story, how it works diagram,
  honest "what it can't do yet", related work (muscle-mem, FlashScript, taprun, Codex
  record-and-replay) with one line on how Amber differs from each.
